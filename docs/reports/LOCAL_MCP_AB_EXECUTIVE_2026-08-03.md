# 图谱 MCP 本机 A/B 实测：汇报摘要

测试日期：2026-08-03  
样本：3 个本机项目，覆盖 C/TypeScript、Vue 2/JavaScript、Java  
任务：定义定位、两跳关系追踪、架构摸底，共 9 组 A/B

## 一句话结论

在 9 个固定任务中，图谱核心查询把工具返回给 Agent 的上下文从 **109,334 个 o200k Token** 降到 **10,194 个**，减少 **90.7%**；直接 CLI 查询中位耗时合计从 **2,944 ms** 降到 **1,685 ms**，减少 **42.8%**。但 Codex 内实际 MCP 工具链路的补充观测出现明显额外延迟，说明下一阶段要优化的是集成链路，而不是图查询本身。

## 主实验

| 指标 | 使用前：纯文本检索 | 使用后：图谱核心查询 | 变化 |
|---|---:|---:|---:|
| 返回内容 Token | 109,334 | 10,194 | **减少 90.7%** |
| 请求 + 返回 Token | 110,531 | 11,177 | **减少 89.9%** |
| 查询耗时合计（中位数） | 2,944 ms | 1,685 ms | **减少 42.8%** |
| 触发 50,000 字符上限 | 6 / 9 | 0 / 9 | 文本基线多项不完整 |
| 工具调用 | 9 | 9 | 持平 |
| 返回语义 | 字符串位置/文件清单 | 定义、qualified name、调用关系、架构聚合 | 结构化提升 |

Token 使用本机 `o200k_base` 分词器精确计数。主指标统计工具返回上下文，不包含模型推理和最终回答；已有索引的首次构建成本也未计入。

## Codex 集成链路观察

另做了 3 个“定位符号 + 直接调用者”的实际 Codex 工具调用。`rg` 三项目中位耗时合计约 0.805 秒；`search_graph + trace_path` 的端到端工具耗时约 37.2 秒。该补测与主实验的任务和调用次数不同，不能替代主 A/B，但清楚暴露了客户端、协议、进程调度或工具宿主链路中的秒级开销。

因此汇报时应区分：

- **核心查询能力**：上下文更少，直接 CLI 实测也更快。
- **当前 Codex 使用体验**：工具链路仍有显著等待，需要分段遥测定位。

## 应该如何讲价值

1. **减少模型阅读量**：即使将纯文本结果强制截断，返回 Token 仍减少 90.7%。
2. **直接提供关系证据**：文本检索只能证明字符串出现；图谱返回已解析的符号与调用边。
3. **复杂任务一次可答**：架构、影响范围、跨服务关系和测试关联不再依赖逐文件拼接。
4. **合理方式是混合路由**：明确字面量继续用 `rg`；关系、影响、架构和跨服务问题走图谱。

## 优先衍生功能

1. **P0：端到端查询遥测**：拆分客户端排队、MCP 传输、进程启动、图查询、序列化耗时，并记录精确 Token。
2. **P0：自适应查询路由**：按任务类型、歧义度、扇入和覆盖状态自动选择文本、图谱或混合方案。
3. **P0：统一分页与截断声明**：所有大结果返回 `has_more`、总数、游标；本次 Java trace 返回 100 项但没有明确截断信息。
4. **P1：PR 影响与回归测试建议**：从 diff 生成受影响入口、文件、测试、跨服务链路和风险级别。
5. **P1：架构上手与漂移报告**：持续生成边界、入口、热点、关键链路和耦合变化。
6. **P2：静态图 + 运行时 Trace 校准**：补足反射、动态注册和事件总线场景。

## 汇报边界

- 本次只有 3 个项目、9 个任务，适合内部决策，不足以代表所有仓库和问题类型。
- 6/9 个文本结果被截断，主 Token 降幅是保守值，但两边答案质量没有经过独立 LLM Judge。
- 索引构建成本未计入，需要用重复查询次数计算摊销点。
- `codebase-memory-mcp-source` 的目标文件无已记录解析缺口，但 freshness 为 `missing`。
- 静态图是 best-effort，不能保证发现所有动态调用。
