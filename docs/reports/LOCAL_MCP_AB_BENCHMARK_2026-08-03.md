# Codebase Knowledge Graph MCP 本机 A/B 实测报告

## 1. 目标与结论

本次评测验证图谱 MCP 在本机真实项目中的上下文成本、查询耗时和结构化价值。

主实验覆盖 3 个项目、3 类任务，共 9 组 A/B。纯文本基线返回 109,334 个 `o200k_base` Token，图谱核心查询返回 10,194 个，减少 **90.7%**。直接 CLI 查询中位耗时合计从 2,944.34 ms 降到 1,684.68 ms，减少 **42.8%**。

补充的 Codex 实际工具调用同时揭示了另一面：图查询核心并不慢，但当前 Codex 到 MCP 的端到端链路存在秒级额外等待，应作为 P0 性能问题单独治理。

## 2. 样本项目

| 项目 | 主要技术栈 | 索引文件 | 图节点 | 图关系 | 索引状态 |
|---|---|---:|---:|---:|---|

## 3. 评测设计

### 3.1 主实验：相同任务的直接 CLI A/B

每个项目执行三类任务：

1. **定义定位**：返回目标符号的 qualified name、文件、行号和签名等信息。
2. **两跳关系追踪**：返回目标符号深度 2 的入向和出向调用关系。
3. **架构摸底**：返回语言、包、入口、热点、边界和层次概览。

纯文本基线使用排序后的 `ripgrep` 字面量/上下文检索或文件清单；图谱侧通过已安装二进制的 `cli search_graph`、`cli trace_path`、`cli get_architecture` 执行相同核心工具查询。每项运行 3 次，取中位数。

两边统一设置 50,000 字符捕获上限。文本基线有 6/9 项达到上限，图谱为 0/9。主 Token 指标使用本机 VS Code 扩展中的 `o200k_base` 分词器精确计数。

### 3.2 补充实验：Codex 端到端工具链路

在当前会话中，对每个项目执行“定位指定符号并找出直接调用者”：

- 基线：一次 `rg`；每项 5 次运行取中位数。
- MCP：`search_graph + trace_path`；每项 3 次运行取中位数。
- Token：只对工具返回文本按 `ceil(字符数 / 4)` 估算。

补充实验的任务、工具调用数和 Token 口径与主实验不同，只用于识别真实客户端链路开销，不能与主实验合并成一个总分。

## 4. 主实验结果

### 4.1 总体

| 指标 | 纯文本基线 | 图谱核心查询 | 变化 |
|---|---:|---:|---:|
| 返回内容 Token | 109,334 | 10,194 | **减少 90.7%** |
| 工具请求 Token | 1,197 | 983 | 减少 17.9% |
| 请求 + 返回 Token | 110,531 | 11,177 | **减少 89.9%** |
| 查询耗时合计（中位数） | 2,944.34 ms | 1,684.68 ms | **减少 42.8%** |
| 触发输出上限 | 6 / 9 | 0 / 9 | 文本结果多项不完整 |
| 工具调用 | 9 | 9 | 持平 |

未截断的纯文本原始输出合计为 1,025,351 Token。该数字说明仓库级字面检索的潜在上下文规模，但实际 Agent 会继续缩小范围，因此正式汇报采用被统一截断后的 109,334 Token 作为更保守的基线。

## 5. Codex 集成链路补充结果

| 项目 / 符号 | `rg` 中位耗时 | MCP 端到端耗时 | `rg` 估算 Token | MCP 估算 Token | Token 降幅 |
|---|---:|---:|---:|---:|---:|
| C：`cbm_store_open_path` | 0.364 秒 | 13.739 秒 | 3,635 | 134 | 96.3% |
| Vue：`getCustomDataPageListOfTable` | 0.336 秒 | 11.562 秒 | 397 | 279 | 29.7% |
| Java：`CurrentUserUtil.getUserLogin` | 0.104 秒 | 11.928 秒 | 33,743 | 3,807 | 88.7% |
| **合计** | **0.805 秒** | **37.229 秒** | **37,775** | **4,220** | **88.8%** |

这组数据不否定主实验。主实验测的是本地二进制核心查询，补充实验测的是当前 Codex 工具调用的端到端等待，且 MCP 每个项目有两次调用。两者差异说明应增加分段遥测，至少区分：

- 客户端排队与工具宿主调度；
- MCP 传输和协议封装；
- 服务进程启动/连接复用；
- 图查询执行；
- 结果序列化和回传。

## 6. 如何解释实际价值

| 效率维度 | 结论 | 决策含义 |
|---|---|---|
| 核心查询耗时 | 图谱合计减少 42.8% | 图查询引擎本身具备实用性能 |
| 当前 Codex 端到端耗时 | 存在明显额外等待 | 优先优化连接复用、调度和遥测 |
| 上下文效率 | 主实验减少 90.7% | 高重复、高扇入和架构任务收益最大 |
| 答案可用性 | 图谱直接返回符号和关系 | 少一次从文本命中推断结构的过程 |

合理定位不是“替代 grep”，而是 AI Agent 的结构化代码理解层：明确字符串、错误信息、配置值继续走文本检索；调用链、影响、架构、跨服务和热点问题走图谱。

## 7. 实际应用场景

1. **PR 影响分析与测试选择**：从 diff 输出直接/间接依赖、入口、测试和跨服务链路。
2. **项目上手与知识传承**：持续生成模块边界、入口、路由、热点和关键调用链。
3. **故障排查**：从接口、异常方法或事件 Channel 追踪上下游路径。
4. **遗留系统治理**：识别高扇入公共函数、重复实现、耦合热点和迁移批次。
5. **跨仓库技术地图**：连接 REST、gRPC、GraphQL、tRPC 和异步消息消费者。
6. **AI 编码 Agent 增强**：用结构化上下文支持重构、测试生成和缺陷修复。

## 8. 衍生功能路线图

| 优先级 | 功能 | 价值 | 本次证据 |
|---|---|---|---|
| P0 | 端到端遥测与自动 A/B 报告 | 量化 Token、分段耗时和摊销点 | 核心 CLI 与 Codex 端到端延迟差异显著 |
| P0 | 自适应查询路由 | 自动选择文本、图谱或混合方案 | 字面量和关系任务的最佳工具不同 |
| P0 | 统一分页与截断声明 | 防止把局部结果误报为全集 | Java trace 返回 100 项但无明确分页元数据 |
| P0 | 常驻连接、缓存与批处理 | 降低真实 Agent 等待 | 当前集成链路有秒级额外开销 |
| P1 | PR 风险报告与回归建议 | 把图谱嵌入评审和 CI | 调用、入口和测试关系可直接复用 |
| P1 | 覆盖度/新鲜度门禁 | 关键结论自动回退源码核验 | 一个样本 freshness 缺失 |
| P1 | 架构快照与漂移检测 | 持续发现边界破坏和耦合增长 | 图中已有边界、热点和层次数据 |
| P1 | 可追溯证据包 | 输出结论、文件行号、qualified name 和覆盖状态 | 适合审计与技术汇报 |
| P2 | 运行时 Trace 校准 | 补足反射、动态注册和事件关系 | 静态图天然存在动态盲区 |
| P2 | 组织级知识图谱 | 连接代码、Owner、ADR、事故和需求 | 从代码图扩展到研发知识资产 |

## 9. 局限与下一轮评测

- 3 个项目、9 个任务仍是小样本，应扩展到 10-20 个按任务类型分层的真实问题。
- 文本基线 6/9 项被截断；图谱输出更完整，但本次没有独立质量 Judge，不能只凭 Token 宣称答案质量提高。
- 问题设计应独立于图谱结果，避免只选择图谱已成功索引的符号。
- 正式 ROI 需要同时记录首次索引、增量更新、完整会话 Token 和第 N 次查询摊销点。
- `codebase-memory-mcp-source` 目标文件无已记录解析缺口，但 freshness 为 `missing`；Vue 和 Java 目标文件为 `metadata_match`。
- 静态分析是 best-effort，反射、动态注册、运行时生成代码和事件总线关系可能缺失。

## 10. 可直接用于汇报的表述

> 本机 3 个真实项目、9 个固定任务实测中，图谱核心查询将返回给 Agent 的上下文从 109,334 个 Token 降至 10,194 个，减少 90.7%；直接 CLI 查询中位耗时合计减少 42.8%。同时，Codex 实际 MCP 调用仍观察到明显集成链路延迟，因此下一阶段重点是端到端遥测、连接复用和自适应路由。
