## 一、汇报口径先统一

### 一句话定位

Codebase Memory MCP 是位于 AI 编码 Agent 与代码库之间的本地结构化代码记忆层。它把源码预先解析为可持久化、可查询的知识图谱，再通过 MCP 向 Codex、Claude Code、Gemini、IDE 和自动化流程提供符号定位、调用追踪、影响分析、架构理解和源码证据。

### 一句话价值

> 把 AI 每次都要重新进行的“目录遍历、关键词搜索、逐文件阅读”，升级为一次构建、持续更新、多个 Agent 复用的结构化代码理解。

### 现场必须守住的三个数据口径

1. 本机 A/B 实测结论是“工具返回上下文 Token 减少 90.7%”，不能说成“研发效率提升 90.7%”。
2. 本机实测覆盖 3 个项目、9 个固定任务，属于内部有效证据，不代表所有语言、仓库和问题类型。
3. 项目论文、README 和 Apple M3 Pro 性能数字要称为“公开基准”或“项目文档数据”，不能称为本次 Windows 环境独立复测。

## 第 1 页：AI 不是缺少代码，而是缺少对代码的结构化记忆

### 屏幕内容

**Codebase Memory MCP**

面向 AI 编码 Agent 的本地代码知识图谱基础设施

一句话：**一次构建，持续更新，多 Agent 复用。**

### 画面设计

- 主画面不要放复杂架构图，只放项目名、一句话和一张真实 3D 图谱截图。
- 背景使用白色或深灰色，强调色用绿色与青色；不要用整页蓝紫渐变。
- 截图右侧只标出三个词：`Symbol`、`Relationship`、`Evidence`。

### 口播稿（约 45 秒）

大家好，我分享的项目是 Codebase Memory MCP。

我们现在使用 AI 写代码，模型能力越来越强，但在真实项目里仍有一个基础问题：AI 每进入一个陌生代码库，都要从目录、搜索和文件阅读重新开始。它拿到了代码，却没有一份可以持续复用的“代码记忆”。

这个项目做的事情，是把代码库从文件集合转换成结构化知识图谱，再通过 MCP 提供给不同的 AI Agent 使用。它不是另一个大模型，而是 AI 与代码库之间的一层本地代码智能基础设施。

### 转场句

为什么这层基础设施有必要？先看 AI 今天是怎么理解一个项目的。

## 第 2 页：传统 AI 代码探索的四个成本

### 屏幕内容

1. **读得多**：目录遍历、全文搜索、整文件回读占用大量 Token。
2. **关系弱**：搜到名字，不等于知道谁调用它、修改会影响谁。
3. **重复做**：新会话、新 Agent、新成员反复探索同一个仓库。
4. **不知边界**：结果为空时，不知道是“不存在”还是“没索引到”。

页脚问题：

> “修改这个公共方法，会影响哪些入口、测试和下游服务？”

### 画面设计

- 左侧画传统流程：`rg -> 打开文件 -> 继续搜索 -> 拼接关系 -> 猜测结论`。
- 右侧只放一个评委能共鸣的问题，不堆功能清单。
- 用红色只标两个风险词：`重复上下文`、`错误推断`。

### 口播稿（约 1 分 20 秒）

传统 Agent 理解代码，主要依赖目录遍历、关键词搜索和逐文件读取。这套方式查错误信息很好用，但面对关系问题会迅速变复杂。

比如我们要回答“修改这个公共方法会影响哪些入口、测试和下游服务”。文本搜索只能证明某个名字出现在哪里，不能直接证明真实调用关系。AI 需要继续打开多个文件，自己拼接导入、类型、继承、路径别名和调用链。项目越大，重复上下文越多，遗漏和误判也越容易发生。

第二个问题是结果不能复用。今天 Codex 探索一遍，明天另一个 Agent 仍要重新探索；新同事加入，也要从头建立认知。

第三个问题更隐蔽：如果搜索结果为空，AI 很容易把“不知道”说成“不存在”。但可能只是目录被忽略、文件发生变化、语法只解析了一部分，或者结果被分页截断。

所以我们要解决的不是“再做一个更快的 grep”，而是让 AI 获得可复用、可追踪、知道自己边界的结构化代码理解。

### 转场句

我们的方案，是把高成本的理解工作从每次会话中前移，变成一次索引和持续增量更新。

## 第 3 页：AI 应用方案——预计算结构，按问题返回最小证据

### 屏幕内容

```text
源码 / 配置 / Git
        ↓
AST + 语义解析
        ↓
持久化代码知识图谱
        ↓
MCP 原子工具
        ↓
AI 组合答案 + 源码证据 + 覆盖边界
```

三个原则：

- **模型无关**：项目自身不内置 LLM。
- **本地优先**：源码和图谱保留在本机。
- **混合路由**：字面量走文本，关系与影响走图谱。

### 画面设计

- 采用一条水平流水线，不要在这一页展开全部模块名。
- AI 图标只放在最右侧，强调图谱负责事实，模型负责理解和表达。
- 在“最小证据”下方放一个窄条：文件、行号、qualified name、关系、覆盖状态。

### 口播稿（约 1 分钟）

方案可以概括成一句话：预先把代码压缩成结构化关系，查询时只给 AI 与问题相关的最小证据。

源码先经过 AST 和语义解析，形成函数、类、接口、路由、配置和基础设施节点，以及调用、导入、继承、使用、数据流和跨服务关系。这些结果持久化保存，不需要每个会话重新计算。

AI 收到自然语言问题后，通过 MCP 选择原子工具。例如符号定位用 `search_graph`，调用关系用 `trace_path`，源码证据用 `get_code_snippet`，架构摸底用 `get_architecture`，覆盖边界用 `check_index_coverage`。

项目自身不包含 LLM。现有 Codex 或其他 Agent 负责理解问题和组织答案，图谱引擎负责确定性查询和返回证据。这样既不绑定模型，也不要求额外 API Key。

这里有一个重要设计：我们不主张替代文本搜索。错误信息、配置值和精确字符串仍然应该走 `rg`；调用链、影响范围、架构和跨服务问题才走图谱。正确的产品形态是自适应的混合路由。

## 第 4 页：技术路径——Tree-sitter + Hybrid LSP + 属性图 + MCP

### 屏幕内容

```mermaid
flowchart LR
    A["文件发现与增量检测"] --> B["Tree-sitter AST"]
    B --> C["Hybrid LSP 语义解析"]
    C --> D["关系构建与质量信号"]
    D --> E["SQLite 持久化图谱"]
    E --> F["搜索 / 路径 / 影响 / Cypher"]
    F --> G["MCP / CLI / HTTP / UI"]
```

技术关键词：

- 内置大规模语言注册表，10 个语言族提供更深 Hybrid LSP 解析；现场以当前二进制 `get_architecture` 返回的语言统计为准。
- 单一静态 C 二进制，本地 SQLite 持久化。
- 图节点、图关系、复杂度、调用证据、覆盖状态统一建模。
- 后台 watcher 与 Git 变化检测支持增量更新。

### 画面设计

- 架构图最多七个节点，每个节点只写一个职责。
- 下方用四个小标签体现性能、语义、持久化、接入面。
- 不在主屏展示 15 个工具名，把工具清单放备份页。

### 口播稿（约 2 分钟）

技术上分为四层。

第一层是语法提取。项目使用 Tree-sitter 把源码解析成语法树，从真实结构中提取函数、类、变量、接口、路由和调用点。相比正则，它能区分注释里的名字、字符串里的名字和真正的代码定义。

第二层是语义解析。只有语法树还不够，例如 `user.profile.displayName()` 到底调用了哪个类型的方法，需要结合导入、返回类型、继承、泛型、方法分派和框架规则。项目在 AST 上增加了轻量级 Hybrid LSP 解析。目前公开 README 对 10 种语言提供更深语义能力，并在当前分支增加了 Vue 2 单文件组件、Vue CLI 和 Webpack 路径别名等遗留前端场景支持。

第三层是图模型。函数、类、路由、文件和模块是节点；`CALLS`、`IMPORTS`、`USAGE`、`IMPLEMENTS`、`DATA_FLOWS`、`HTTP_CALLS` 等是边。图遍历可以直接回答入向调用、出向依赖、两跳影响和跨服务链路。复杂度、扇入、循环深度和解析证据也作为属性保存，方便做热点和风险排序。

第四层是交付。图谱保存在本地 SQLite 中，通过 MCP、CLI、HTTP 和可视化 UI 提供能力。后台 watcher 检测变化，只对增量部分更新。团队还可以共享压缩图谱快照，让其他成员不必从零重建。

当前项目的关键不是单一算法，而是完整工程链路：多语言解析、关系构建、持久化、增量刷新、可信元数据、Agent 接入和跨平台交付被放在同一个本地基础设施里。

### 技术讲解加深版（评委追问时使用）

1. **为什么是属性图**：代码天然是多关系网络。同一函数既有调用方，也有测试、文件、路由、配置和服务关系，属性图比扁平文档块更适合多跳查询与影响传播。
2. **为什么使用 SQLite**：单机研发场景更看重零运维、可移植、事务和本地性能，不需要先引入独立图数据库集群。图遍历和 openCypher 子集由项目自身执行。
3. **为什么不是纯 LSP**：传统 LSP 通常以编辑器当前工程和单语言交互为中心；本项目需要跨语言、跨仓库、可持久化、可聚类、可离线复用的统一图模型。
4. **为什么不是纯向量搜索**：向量检索擅长“意思相近”，但不能可靠证明“谁调用谁”。项目把 BM25、语义向量与确定性关系查询组合使用。

## 第 5 页：设计层——不是展示一张“毛线球”，而是帮助用户完成决策

### 屏幕内容

三个设计闭环：

1. **从全局到局部**：架构概览 -> 模块 -> 符号 -> 调用路径。
2. **从结论到证据**：风险结论 -> 关系边 -> 文件与行号 -> 源码。
3. **从结果到边界**：答案 -> 新鲜度 -> 覆盖度 -> 截断状态 -> 回退建议。

用户界面：项目、图谱、影响、热点、文件风险、服务控制、日志。

### 画面设计

- 使用真实 UI 截图，叠加三条细箭头表示“概览、下钻、证据”。
- 不要只放 3D 图。补一张右侧详情栏或影响分析视图，说明 UI 为任务服务。
- 状态颜色固定：绿色为已验证，黄色为不确定，红色为高风险，灰色为未覆盖。

### 口播稿（约 1 分 5 秒）

设计层面，我们不希望用户看到的只是一张很炫但无法使用的关系图。真正的目标是帮助开发者、架构师和管理者完成理解、定位和决策。

第一个闭环是从全局到局部。用户先看语言、入口、模块边界和热点，再下钻到具体符号和调用路径，而不是一开始就面对几万个节点。

第二个闭环是从结论到证据。系统可以说某个改动风险高，但必须允许用户继续点到关系边、文件、行号和源码。AI 的总结是入口，源码才是最终证据。

第三个闭环是从结果到边界。如果项目有未索引目录、部分解析区间、文件已经变化或结果被截断，界面和工具响应都要显式说明。我们把“unknown”作为一等状态，避免把未知包装成确定答案。

桌面端“风暴之眼”负责服务启停、端口、进程、内存、日志和更新；图谱控制台负责分析。一个解决运行问题，一个解决理解问题，职责分开。

## 第 6 页：现场演示——四步回答一个真实关系问题

### 演示问题

> “索引仓库的 MCP 入口在哪里？它向下调用哪些关键模块？当前结论是否覆盖完整？”

### 推荐演示流程（2 分 15 秒）

#### 第一步：架构概览（30 秒）

向 Agent 提问：

> 请使用代码图谱概括当前项目的语言、核心模块、入口、热点和模块边界。

预期工具：`get_architecture`

讲解点：一次调用直接得到聚合后的架构信息，而不是把 700 多个文件名交给模型自行归类。

#### 第二步：定位符号（25 秒）

向 Agent 提问：

> 定位 `handle_index_repository` 的精确定义，并给出 qualified name。

预期工具：`search_graph`

预期证据：`src/mcp/mcp.c` 中的 `handle_index_repository`，当前索引定位到 6557-6713 行。

#### 第三步：追踪关系（50 秒）

向 Agent 提问：

> 追踪 `handle_index_repository` 两层出向调用，并区分高置信语义解析与启发式关系。

预期工具：`trace_path`

讲解点：当前图谱可看到它连接 MCP 分发、索引监督、pipeline、store、workspace 安全校验和 artifact bootstrap 等模块；返回中还可以带解析策略与置信度，而不只是名字列表。

#### 第四步：回到源码与覆盖边界（30 秒）

向 Agent 提问：

> 返回该函数源码片段，并检查目标文件与相关范围的索引覆盖状态。

预期工具：`get_code_snippet` + `check_index_coverage`

收束语：图谱负责缩小范围和建立关系，源码回读负责最终核验，覆盖检查负责说明我们是否有资格下确定结论。

### 演示画面操作建议

1. 左侧保持 Agent 对话，右侧保持 3D 图谱或调用路径视图。
2. 每次只高亮一个变化：架构聚合、符号定位、调用路径、源码证据。
3. 不要现场首次索引大型业务仓库；提前完成索引，只演示查询。
4. 预先把结果截图和关键 JSON 保存在备份页；出现客户端链路延迟时立即切静态演示，不等待超过 8 秒。

### 现场演示失败时的替代口播

这里需要区分图查询核心和 Agent 到 MCP 的端到端链路。我们的本机 CLI A/B 显示核心查询整体更快，但当前 Codex 工具宿主链路仍存在额外等待。因此我准备了同一查询的预录结果。我们下一阶段的 P0 工作正是分段遥测、常驻连接和查询批处理，而不是回避这个问题。

## 第 7 页：效果与价值——上下文更少，关系证据更直接

### 屏幕内容

本机 3 个真实项目、9 个固定任务 A/B：

| 指标 | 使用前：纯文本检索 | 使用后：图谱核心查询 | 变化 |
|---|---:|---:|---:|
| 返回内容 Token | 109,334 | 10,194 | **减少 90.7%** |
| 请求 + 返回 Token | 110,531 | 11,177 | **减少 89.9%** |
| 查询耗时合计（中位数） | 2,944 ms | 1,685 ms | **减少 42.8%** |
| 触发 50,000 字符上限 | 6 / 9 | 0 / 9 | 完整性改善 |
| 工具调用 | 9 | 9 | 持平 |

分任务 Token 降幅：

- 定义定位：99.1%
- 两跳关系：81.2%
- 架构摸底：91.6%

### 画面设计

- 主视觉只突出 `90.7%`，不要同时放五个超大数字。
- 表格下方加一句小字：主指标为工具返回上下文，不含模型推理和首次索引成本。
- 使用前与使用后使用中性灰和绿色，避免夸张的红绿对立。

### 口播稿（约 1 分 20 秒）

我们在本机选择了三个真实项目，覆盖 C/TypeScript、Vue 2/JavaScript 和 Java，设计了定义定位、两跳关系和架构摸底三类任务，共 9 组 A/B。

纯文本侧返回给 Agent 的上下文是 109,334 个 Token，图谱侧是 10,194 个，减少 90.7%。请求加返回合计减少 89.9%。直接 CLI 核心查询的中位耗时合计从 2,944 毫秒降到 1,685 毫秒，减少 42.8%。

更重要的是输出语义发生了变化。文本侧给出的是字符串位置和文件清单，图谱侧直接给出定义、限定名、调用关系和架构聚合。纯文本结果有 6 项触发统一字符上限，图谱侧 0 项。

但我不会把这组数据说成“研发效率提升 90.7%”。它证明的是上下文效率和核心查询效率。首次索引成本、完整会话耗时、答案质量和最终人效，还需要在更大样本上持续评测。

另外，我们也测到了当前 Codex 端到端 MCP 链路存在秒级额外等待。这说明核心查询引擎已经有收益，但客户端排队、协议、进程连接和结果回传仍需要 P0 级优化。这个问题会在路线图里通过分段遥测、连接复用和批处理解决。

### 业务价值换算方式

不要直接给没有依据的金额。建议使用以下 ROI 公式由试点数据换算：

```text
月度收益
= 月查询次数 × 单次减少的 Agent 成本
+ 影响分析节省的人时 × 人时成本
+ 提前发现回归问题的期望损失减少
- 索引、部署和维护成本
```

试点阶段重点记录四个指标：完整会话 Token、完成任务时间、人工复核准确率、PR 回归遗漏率。

## 第 8 页：与 Understand-Anything Skill 的区别

### 先给结论

两者都使用 Tree-sitter 和知识图谱，也都支持可视化与增量更新，但产品重心不同：

> **Understand-Anything 更偏“让人快速看懂项目”的 Skill/插件与知识导览产品；Codebase Memory MCP 更偏“让 Agent 持续、低成本、可审计地查询代码关系”的本地代码智能基础设施。**

它们不是简单的二选一，更像上层认知体验与底层查询能力的两种不同实现重心。

### 对比表

| 维度 | Codebase Memory MCP | Understand-Anything |
|---|---|---|
| 核心定位 | 面向 Agent 的持续查询、关系分析与代码记忆层 | 面向人和 Agent 的项目认知、知识导览与可视化 Skill/插件 |
| 主要入口 | MCP 原子工具、CLI、HTTP、3D 控制台 | `$understand` / `/understand` 等 Skill 命令与 Dashboard |
| 分析主链路 | Tree-sitter + Hybrid LSP + 多阶段静态关系构建 | Tree-sitter 确定性结构提取 + 多 Agent/LLM 语义增强 |
| LLM 依赖 | 建图与查询均不要求内置 LLM；复用现有 MCP 客户端模型 | 初次完整分析会使用 LLM 生成摘要、标签、架构层、业务域和导览；可改用本地模型 |
| 首次成本 | 主要是本地 CPU、内存和索引时间 | 公开 README 明确提示大型项目首次分析可能消耗较多 Token |
| 存储形态 | 本地 SQLite 图谱，可导出压缩共享快照 | `.ua/knowledge-graph.json` 等 JSON 资产，可提交到 Git，较大文件建议 Git LFS |

### 口播稿（约 1 分钟）

评委可能会问，既然已经有 Understand-Anything，为什么还要做这个项目？

我先承认相同点：两者都使用 Tree-sitter 构建知识图谱，都有可视化、增量更新和影响分析。Understand-Anything 公开 README 展示了非常优秀的人类认知体验，包括多 Agent 流水线、自然语言摘要、业务域映射、Guided Tour 和角色自适应界面。这些是它明显更强的方向。

差异在于重心。Understand-Anything 的核心入口是 Skill/插件命令，首次分析使用 LLM 为结构补充摘要、标签、架构层和业务语义，适合“第一次把项目讲明白”。它也明确提醒，大型项目首次分析可能消耗较多 Token。

Codebase Memory MCP 的重点是建立不依赖额外 LLM 的本地静态分析与查询服务。Agent 可以在每次编码任务中调用细粒度 MCP 工具，只取当前问题需要的最小关系证据；同时获得 qualified name、置信度、覆盖度、新鲜度和源码回读路径。它更适合高频查询、PR 影响、CI 门禁、跨仓关系和长期团队复用。

所以我们的回答不是“它不好、我们更好”，而是：Understand-Anything 偏认知与表达，我们偏查询与工程治理。如果未来组合，完全可以让 Codebase Memory MCP 提供高置信结构关系，让 Understand-Anything 一类上层产品负责业务语义、导览和角色化呈现。

### 评委追问时的关键句

> Skill 定义的是 Agent “应该如何工作”，MCP 提供的是 Agent “可以反复调用什么能力”。Skill 可以编排流程，但如果底层没有持久化、可查询、可校验的代码分析服务，每次编排仍可能重新读取和重新推断。

## 第 9 页：复制推广——从个人提效到组织级研发治理

### 屏幕内容

```text
阶段 1：个人试用       1 个仓库 / 5-10 名开发者
阶段 2：团队试点       PR 影响 + 项目上手 + Vue 迁移
阶段 3：平台接入       统一远程 MCP + ACL + 审计 + 指标
阶段 4：组织推广       代码 + 文档 + Owner + 事故 + ADR
```

### 口播稿（约 45 秒）

推广计划分四步。

第一步选一个高频修改、关系复杂、已有痛点的仓库，用 5 到 10 名开发者做两到四周试点。只验证三类任务：新成员上手、公共方法影响分析、故障链路定位。

第二步接入 PR 评论模式，先只提示、不阻断。记录建议被确认、忽略和误报的比例，同时沉淀 Vue 2/Webpack 迁移规则，这是当前分支最有业务差异化的场景。

第三步建设团队统一远程 MCP，增加项目目录、ACL、审计、限流和 P50/P95/P99 遥测。源码仍在内网处理，客户端只获取授权项目的最小证据。

第四步再连接文档、Owner、ADR、事故和运行时 Trace，形成组织级软件资产图谱。只有前面三步产生稳定使用数据后，才考虑多节点和更大平台化投入。

### 推广验收指标

| 维度 | 指标 |
|---|---|
| 使用 | 周活用户、活跃项目、每周有效图谱查询数 |
| 效率 | 完成影响分析时间、新人找到核心入口时间、完整会话 Token |
| 质量 | 关键上下文召回率、关系人工确认率、误报率、unknown 正确披露率 |
| 工程 | 索引成功率、增量更新时间、MCP P50/P95/P99、generation 过期比例 |
| 业务 | PR 回归遗漏率、迁移评估耗时、事故定位时间 |

### 推广中的边界控制

1. 试点期不把图谱结论直接作为合并阻断条件。
2. 高风险结论必须回到源码或运行时证据。
3. 动态调用密集项目先做准确率基线，再决定是否推广。
4. 对外统一语言数量、测试数量和基准口径后再形成正式宣传材料。

## 四、必答题：如果评委问“这个项目你做了什么？”

这是最需要提前准备的问题。不要把自己讲成“只加了一个 Vue 解析器”，也不要把上游能力包装成从零原创。更准确的身份是：**开源底座上的核心引擎贡献者、工程交付负责人和实际场景验证者。**

回答时先承认上游，再主动把话题拉回当前 fork 解决的六类真实问题：代码理解、依赖生态、语义收束、可信回答、产品交付和效果实证。

### 30 秒现场短答

> 项目基于上游开源底座，但我做的不只是 Vue 解析。我主要推进了三类工作：核心引擎上增强 Java 继承/重写、Fastjson 等外部依赖调用建模，并落地本地语义候选收束和架构可信降噪；工程上解决索引原子发布和并行一致性；交付上完成图谱工作台、Windows 桌面端、自动升级和跨平台发布。最后用 3 个真实项目、9 个任务验证，返回上下文 Token 减少 90.7%，核心查询中位耗时合计减少 42.8%。我的贡献是把开源底座推进成能理解复杂项目、可信且可交付的团队工具。

如果现场时间只够一句话：

> 我不是简单包装开源项目，而是同时参与了核心索引与关系生成、查询可信性、桌面产品化、发布链路和真实项目验证，把“能跑的开源底座”推进成“能在复杂项目里稳定使用的研发工具”。

### 2 分钟展开答

我会先把继承边界说清楚，再讲六条贡献主线。

**第一，上游继承。**

Tree-sitter 语法解析、基础代码图谱、MCP 工具和部分通用静态分析能力来自上游开源项目。这个归属我们会明确说明，不把上游成果包装成个人原创。

**第二，代码理解引擎增强。**

我们补的不只是 Vue。前端侧增加了 `.vue` 单文件组件二次解析、原始行号回映射，以及 Vue CLI、Webpack 和 `tsconfig/jsconfig` alias 还原；Java 侧增强了 `IMPLEMENTS`、`INHERITS`、`OVERRIDE` 等面向对象关系，并把 `com.alibaba.fastjson.JSON`、`JSONObject` 这类仓库外部类型表示成 `ExternalType`，把 `JSON.toJSONString`、`JSONObject.parseObject` 表示成 `ExternalMethod`，再建立业务方法到外部方法的 `CALLS`。这让图谱从“只理解仓库内部符号”向“理解业务代码如何依赖外部 SDK”迈了一步。

Fastjson 的价值不在于多识别一个库，而在于建立了一类可推广的外部依赖建模方法。它可以为依赖升级影响评估、三方库替换、漏洞排查和技术债盘点提供候选影响面。当前能力边界也要说明：已经建立外部类型、方法和调用关系，但尚未把 Maven 版本、许可证、CVE 和第三方源码全部纳入图谱。

**第三，语义检索和图关系收束。**

当前 fork 集成并落地了本地语义表示体系：综合 TF-IDF/随机索引、API、类型、装饰器、调用邻居、AST profile 和 MinHash 代码指纹等特征；再对语义向量生成随机超平面签名，通过 LSH 分桶把全量函数两两比较收缩为有限候选，最后做多信号评分。超过阈值的候选不会无限连边，而是按每个节点的 `max_edges` 预算收束为稀疏的 `SEMANTICALLY_RELATED` 关系。评分阶段可以并行，最终按规范顺序串行准入，避免线程调度导致同一次索引生成不同边集。

这里解决了三个工程问题：不依赖外部向量数据库和额外 API Key；避免全量两两比较带来的规模膨胀；避免语义边过密和并行结果抖动。它是“索引阶段的候选和边收束”，与最近做的架构回答收敛是两件事。

**第四，回答可信性和索引可靠性。**

架构查询的收敛重点不是继续返回更多内容，而是让 Agent 知道哪些结论可信、何时停止继续查。我们给不同架构分区增加 `section_status`、`confidence` 和 `reason`，给整体结果增加 `stop_recommended` 和 `next_action`；默认架构回答只返回高价值摘要，按目录范围聚合模块；热点只统计高置信的不同调用者，边界过滤低置信调用，Vue 普通生命周期方法不再被误当成系统入口。

存储侧则补了 SQLite 索引原子发布：构建过程中不提前破坏旧库，成功后再切换，失败时保留可用旧索引；同时覆盖 WAL/SHM 清理、旧 reader 存活、中文路径和 Windows 文件占用重试。我们还增加串行与并行索引结果一致性测试。它们共同保证“查得准”之外还要“更新失败不丢库、不同线程数结果不漂移”。

**第五，产品化与团队交付。**

图谱 UI 从单纯的 3D 展示器扩展为可以管理项目、单项目更新、顺序更新全部项目、查看进度和失败原因，并提供分析、影响和热点视图的工作台；桌面端负责服务启停、日志、跨窗口服务接管、升级和恢复，同时通过 token 验证和进程身份检查避免误接管、误终止其他进程。发布侧补齐 Windows/macOS 构建、Installer、DMG、checksum、VirusTotal 和 Release 门禁。这些工作把源码能力变成普通团队成员可以安装、升级和持续使用的产品。

**第六，查询表达力和效果实证。**

我们还增强了 openCypher 子集，例如关系 `type()` 过滤、`split(...)[n]`、`SUM(CASE...)`、字面量投影和 `UNION ALL` 等，使模块聚合、多跳和复杂筛选不必为每个问题新增一个专用接口。最后，用 C、Vue/JavaScript 和 Java 三个真实项目完成 9 个任务的 A/B：图谱工具返回上下文从 109,334 Token 降到 10,194 Token，减少 90.7%；核心 CLI 查询中位耗时合计从 2,944 毫秒降到 1,685 毫秒，减少 42.8%。同时披露 Codex 端到端 MCP 仍有额外延迟，把下一阶段优化目标也公开出来。

所以，如果用一句话概括我的工作：**我参与的不是单点解析适配，而是从核心关系生成、依赖生态建模和结果收束，到索引可靠性、桌面交付、发布治理和效果验证的一整条落地链路。**

## 五、评委深度答疑库

## Q1：这个项目到底哪里用了 AI？它自己又没有模型。

**短答：** AI 在 MCP 客户端侧负责理解自然语言、选择工具和组织答案；本项目负责把代码变成 AI 可查询的结构化事实。它是 AI 应用的“上下文基础设施”，不是模型本身。

**深答：** 一个完整 AI 应用不只有模型，还包括数据准备、上下文检索、工具执行、证据校验和运行治理。Codebase Memory MCP 把高成本、易重复的代码理解前移为静态分析，并通过标准协议服务多个模型。这样模型替换时，代码知识资产无需重建应用逻辑。

## Q2：为什么不用 `grep` 或 `ripgrep`？

**短答：** 精确字符串仍然用 `rg`；图谱只接管关系、影响、架构和跨服务问题。

**深答：** `rg` 证明字符串出现，不能直接证明符号定义、类型分派或调用关系。例如同名方法可能出现在接口、实现、测试、注释和字符串中。图谱把这些结果规范成 qualified name 和关系边。最佳方案是混合路由，而不是互相替代。

## Q3：为什么不用向量数据库做代码 RAG？

**短答：** RAG 擅长语义相似，图谱擅长确定性关系，二者解决不同问题。

**深答：** “哪里处理鉴权”适合语义召回；“谁调用 `validateToken`”需要调用图；“改动会影响哪些入口和测试”需要多跳影响传播。项目内部也有 BM25 和语义向量，但最终用图关系提供可验证路径，避免把语义相似误当成真实依赖。

## Q4：IDE 已经有 Language Server，为什么还要 Hybrid LSP？

**短答：** IDE LSP 服务当前编辑体验，本项目服务跨会话、跨语言、跨仓库的持久化查询与图分析。

**深答：** LSP 通常是单语言、会话态、面向“跳转到定义”等交互。本项目把部分类型推导和方法分派能力内置到索引阶段，再统一保存为图关系，从而支持聚类、影响传播、跨仓连接、历史复用和 MCP 查询。它不是完整复刻每个语言服务器，而是为图关系质量选择性实现高价值语义规则。

## Q5：静态分析遇到反射、动态注册、依赖注入怎么办？

**短答：** 不承诺 100% 完整；用 best-effort 静态图、置信度和运行时 Trace 形成闭环。

**深答：** 静态图对显式定义、导入、继承和大部分调用关系有效，但反射、运行时生成代码、事件总线和动态依赖注入可能缺失。系统通过解析证据、置信度、覆盖状态和回源码建议披露边界。下一阶段接入 OpenTelemetry、测试覆盖率和生产 Trace，用运行时事实校准静态边。

## Q6：图谱返回空结果，怎么证明代码里真的没有？

**短答：** 不能只凭空结果证明不存在，必须同时检查覆盖度、新鲜度和分页状态。

**深答：** `check_index_coverage` 会报告未索引目录、跳过文件、部分解析区间和文件元数据变化；工具结果还需要携带 `has_more`、总数和游标。只有覆盖条件满足时，才能给出较强的否定结论，否则应该返回 unknown 并回退源码搜索。

## Q7：首次索引也有成本，90.7% Token 降幅是否忽略了它？

**短答：** 是的，当前主指标不含首次索引成本，所以我们明确披露，并用重复查询次数计算摊销点。

**深答：** 本项目首次索引主要消耗本地 CPU、内存和时间，不消耗额外 LLM Token；收益随复用次数增加。正式 ROI 要同时测首次全量索引、增量更新、第 N 次查询、完整 Agent 会话和团队复用次数，计算何时覆盖索引成本。

## Q8：你们的 A/B 是否公平？纯文本结果 6/9 被截断，会不会刻意放大收益？

**短答：** 两边统一使用 50,000 字符上限，正式采用截断后的文本 Token 作为保守基线；但本轮没有独立答案质量 Judge，因此不宣称质量提升了具体百分比。

**深答：** 主实验两侧执行相同任务，每项运行 3 次取中位数，Token 使用 `o200k_base` 精确计数。文本未截断原始输出更大，但真实 Agent 会继续收窄范围，所以没有采用百万 Token 数字做主结论。下一轮应由独立问题设计者和盲评 Judge 评估正确性、完整性与证据质量。

## Q9：为什么本机 CLI 更快，但 Codex 实际 MCP 调用反而慢？

**短答：** 核心图查询和端到端工具链路是两个不同层次，当前瓶颈在客户端排队、协议、进程连接或宿主调度。

**深答：** 主实验测二进制 CLI 核心查询；补充实验测 Codex 到 MCP 的完整路径，而且 MCP 侧每个任务有两次调用，不能直接合并比较。补测明确暴露秒级额外等待。P0 工作是增加分段 Trace，分别记录排队、传输、进程、SQL/图查询、序列化和回传耗时，再做常驻连接、缓存和批处理。

## Q10：为什么用 SQLite，不用 Neo4j 或其他图数据库？

**短答：** 个人与团队单节点研发场景优先零运维、单文件、可移植和本地性能。

**深答：** 引入独立图数据库会增加部署、认证、备份和版本管理成本。本项目在 SQLite 中存储节点、边、FTS 和向量数据，自行执行遍历与 openCypher 子集。达到组织级并发和容量上限后，再根据真实指标评估远程服务或多节点，而不是提前平台化。

## Q11：158 种语言是否都达到同样质量？

**短答：** 不是。公开支持表示可解析覆盖，不等于每种语言都有同等语义深度。

**深答：** Tree-sitter grammar 提供广覆盖；Hybrid LSP 语言拥有更深的类型、泛型和方法分派能力；模板、配置和领域语言主要提取其适合的结构。正式推广应按语言和任务维度公开准确率，不使用一个总数字掩盖差异。

## Q12：如何保证图谱及时更新？

**短答：** 全量索引后使用 watcher、Git 变化检测和增量 pipeline，同时在查询时检查 generation 与文件 freshness。

**深答：** 更新不仅是重新扫文件，还要处理被删除符号、变化关系、跨文件引用和缓存失效。可信响应应携带索引 generation、索引时间和元数据匹配状态。关键查询发现文件已变更时，应先增量更新或直接回读源码。

## Q13：代码安全怎么保证？

**短答：** 默认本地处理，不需要把源码发送给额外模型服务；控制台只绑定 loopback。

**深答：** 单机模式的源码、SQLite 图谱和查询都留在本机。团队远程模式需要进一步增加项目级 ACL、OIDC/Token、审计、速率限制、允许工具列表和最小结果返回。还要把安装器、升级链和发布产物纳入安全治理，包括校验和、签名、SBOM 和来源证明。

## Q14：相比 Understand-Anything，最核心的不可替代点是什么？

**短答：** 不是不可替代，而是基础设施重心不同：本项目强调无额外 LLM 的持续查询、细粒度工具、代码关系证据和可信边界。

**深答：** Understand-Anything 的优势是多 Agent 语义增强、业务域、Guided Tour 和角色化 UI，特别适合人类上手。其 README 也明确大型项目首次分析可能消耗较多 Token。本项目把主要成本放在本地静态索引，随后通过 MCP 原子工具服务高频任务，更适合 PR、CI、影响分析与跨 Agent 复用。实际产品可以组合，而不是重复造一套上层导览。

## Q15：Skill 和 MCP 本质区别是什么？

**短答：** Skill 是工作说明与流程编排，MCP Server 是可被重复调用的能力与数据服务。

**深答：** 一个 Skill 可以告诉 Agent 按什么步骤扫描、分析和输出，但数据是否持久化、查询是否确定、关系是否可复用、覆盖度是否可校验，取决于底层工具。MCP 把能力做成标准协议接口，可被不同 Agent 共享。最理想的形态是 Skill 编排 MCP，而不是把二者当成同一层。

## Q16：Understand-Anything 也有 Tree-sitter、增量更新和影响分析，你们是否重复建设？

**短答：** 底层技术有重叠，但目标函数不同；重复部分应客观承认，差异要落在查询契约、语义深度、运行成本和工程场景上。

**深答：** 两者都需要文件扫描、AST、图和 UI，这些是问题本身决定的共同基础。Understand-Anything 用 LLM 增强摘要、标签、架构层和业务流程；本项目用 Hybrid LSP、调用/数据流/跨服务边、覆盖度与细粒度 MCP 工具强化 Agent 查询。评估时应该用相同仓库和任务比较正确率、完整会话 Token、首次分析成本、增量成本、查询延迟和人工决策效果，而不是只比功能表。

## Q17：项目如何避免 AI 幻觉？

**短答：** 不声称消灭幻觉，而是缩小模型自由推断空间，并强制返回结构化证据与不确定性。

**深答：** 模型仍可能解释错误，但图谱能把“可能相关的文件”收缩为明确的定义、关系边、参数表达式和源码行。响应同时说明关系解析策略、置信度、覆盖缺口和截断状态。高风险结论再回读源码或运行时证据，形成多层校验。

## Q18：怎么证明最终有业务价值，而不只是 Token 好看？

**短答：** 用任务完成时间、人工复核准确率、PR 回归遗漏和事故定位时间证明，Token 只是前置指标。

**深答：** Token 降低可以带来成本和延迟收益，但业务价值要落到研发流程。试点至少记录新人找到入口的时间、公共方法影响分析时间、建议测试被采用比例、误报率、PR 返工、线上回归和故障定位时间。只有这些指标改善，才进入组织推广。

## Q19：哪些场景不适合使用？

**短答：** 小型一次性仓库、纯文本问题、动态元编程极重且缺少运行时证据的项目，收益可能不足。

**深答：** 如果项目只有少量文件，首次索引摊销价值小；如果问题只是找错误字符串，`rg` 更直接；如果核心行为高度依赖反射、运行时脚本生成或外部编排，静态图只能做候选分析。产品必须能判断这些场景并自动回退。

## Q20：项目下一步最重要的不是增加什么功能，而是什么？

**短答：** 先建立可信响应契约和真实使用指标，再增加高层功能。

**深答：** 当前最优先的是统一 generation、freshness、coverage、pagination、confidence 和 evidence；同时补齐端到端遥测和更大样本 A/B。在此基础上再建设 `build_context`、PR 风险报告、测试推荐、Vue 迁移和组织级服务。没有可信元数据的更多结论，只会放大错误。

## Q21：Fastjson 的第三方调用是怎么识别的？如何避免和项目内同名 `JSON` 类误绑定？

**短答：** 不按类名猜，而是先读取当前文件的显式 import，把完整包名建成外部类型，再让调用限定符通过该 import 映射到外部方法。

**深答：** 对 `import com.alibaba.fastjson.JSON`，索引器先生成 qualified name 包含完整包路径、带 `external=true` 的 `ExternalType`，并建立文件到该类型的 `IMPORTS`。处理 `JSON.toJSONString(...)` 时，先取 `JSON` 作为限定符，只在当前文件的 import map 中查找；命中外部类型后，再生成其下的 `ExternalMethod` 并建立业务方法到外部方法的 `CALLS`。回归测试专门同时定义本地 `probe.JSON` 和 Fastjson import，验证显式 import 优先，不让本地同名类劫持调用。当前边界是静态显式 import 和方法关系，不等于已经读取 Maven 版本、下载依赖源码或完成 CVE 自动匹配。

## Q22：你说的“向量收束”和最近的“架构结果收敛”有什么区别？

**短答：** 前者发生在索引阶段，控制哪些函数成为语义候选和关系边；后者发生在查询阶段，控制 Agent 收到多少架构内容、结论有多可信以及是否应该停止深挖。

**深答：** 语义候选收束先组合文本、API、类型、调用邻居、AST profile 和 MinHash 指纹等信号，对语义向量做 LSH 分桶，将潜在的全量两两比较缩到每个函数至多有限候选；候选经阈值评分后，再受每节点 `max_edges` 预算限制，最终按确定性顺序生成稀疏语义边。架构结果收敛则给 `get_architecture` 增加分区状态、置信度、原因、停止建议和下一步动作，默认只返回摘要，并过滤低置信热点、边界和伪入口。提交 `5bc92583` 对应的是后一类，不能把它说成“修复了向量算法收敛”。

## 六、备份页：18 个 MCP 工具如何分工

正式演示不必全部展示，答疑时按问题类型说明：

| 问题类型 | 优先工具 | 返回价值 |
|---|---|---|
| 符号在哪里 | `search_graph` | 定义、类型、qualified name、文件与行号 |
| 谁调用谁 | `trace_path` | 入向、出向、多跳、数据流、跨服务路径 |
| 读取精确实现 | `get_code_snippet` | 单个函数/类的边界化源码 |
| 项目怎么组织 | `get_architecture` | 语言、包、入口、热点、边界、层次、社区 |
| 复杂多跳问题 | `query_graph` | openCypher 子集聚合与路径查询 |
| 改动影响谁 | `detect_changes` / `explain_impact` | 受影响符号、入口、测试与风险分级 |
| 一次性准备任务上下文 | `build_context` | 按目标、证据等级和 Token 预算编译可回溯证据包 |
| 结果是否可信 | `index_status` / `check_index_coverage` | 缺口、新鲜度、未索引和回退建议 |
| 精确字面量 | `search_code` 或 `rg` | 错误信息、配置值、字符串匹配 |
| 长期架构意图 | `manage_adr` | 跨会话保存架构决策 |

讲解原则：工具数量不是卖点，按问题把上下文压缩成高密度证据才是卖点。

4. 录制一段不超过 90 秒的查询视频，作为链路延迟时的替代材料。
5. 把本机 A/B CSV、摘要和完整报告放入备份目录。
6. 检查 UI 端口、桌面服务状态、浏览器缩放和中文字体。

### 演示前 15 分钟

1. 启动桌面控制器和图谱控制台。
2. 验证 Agent 可以列出项目并执行一次轻量查询。
3. 关闭无关通知、终端和浏览器标签。
4. 将演示窗口布局固定为左侧对话、右侧图谱。
5. 打开静态备份页，但不要让评委看到切换准备过程。

### 不要做的事

- 不现场全量索引大型仓库。
- 不把公开基准说成本机实测。
- 不用“完全准确”“零幻觉”“替代所有搜索”等绝对表述。
- 不攻击 Understand-Anything、RAG、LSP 或 `rg`；明确各自最适用的问题。
- 不在 15 分钟内展示所有功能。

## 九、最后 30 秒背诵版

Codebase Memory MCP 解决的是 AI 每次进入代码库都要重复搜索、重复阅读、重新推断关系的问题。它通过 Tree-sitter、Hybrid LSP 和知识图谱，把代码预先转换为可复用的结构化事实，再通过 MCP 向多个 Agent 提供符号、调用、影响、架构和源码证据。

本机 3 个项目、9 个任务的 A/B 中，工具返回上下文 Token 减少 90.7%，核心查询中位耗时合计减少 42.8%。我们同时诚实看到 Codex 端到端链路仍有额外延迟，下一步会优先做可信响应、分段遥测和混合路由。

相比 Understand-Anything，我们更偏持续在线、无额外 LLM 的代码关系查询底座；它更擅长业务语义、Guided Tour 和角色化可视化。两者可以互补。最终目标不是让 AI 读取更多代码，而是让它使用更少、更准、可验证的代码证据。
